# DigiGrowth OS

Full-stack client acquisition platform. Stack: React + Vite frontend, FastAPI + asyncpg backend, PostgreSQL, deployed on Railway via Docker.

## Directory Structure

- `context/offer.md` — **DigiGrowth's reference offer terms** (PT patient acquisition: prepaid $49 assessments, pay per booking, 7-10 paid assessments in 30 days, 7 guaranteed, standard vs. 3-clinic pilot pricing). There is no default offer: each prospect/client gets their own, set on the sales call or Blueprint and saved in `media-buying-agent/clients/<slug>/client-context.md` "## Offer". Use offer.md for the reference figures and pilot terms, never present them as THE offer.
- `context/cold-email-deliverability.md` — **cold email deliverability SOP** (warm-up, caps, sending checklist) plus DigiGrowth's current gaps against it. Read before touching email identities, sequence copy/caps, DNS or the video link.
- `context/positioning.md` — **how the offer is framed** in website/conversion copy: guarantee leads, the "Digital Makeover" is the named-but-never-explained mechanism behind it (builds curiosity for the call). Framing only; terms still come from `offer.md`.

- `dashboard/frontend/src/panels/` — React panel components (one per nav tab)
- `dashboard/backend/routers/` — FastAPI routers (one per feature area)

- `dashboard/backend/db.py` — asyncpg pool + schema creation
- `dashboard/backend/agents_registry.json` — agent metadata (id, name, root_dir, color)
- `dashboard/backend/dialer_engine.py` + `dashboard/backend/routers/dialer.py` + `dashboard/backend/routers/dialer_webhooks.py` — Twilio parallel dialer (up to 10 simultaneous calls), browser-based via `dashboard/frontend/src/panels/DialerPanel.jsx` and Twilio Voice JS SDK — no separate local script or ngrok needed
- `dashboard/Dockerfile` — multi-stage build: Node 20 Alpine (frontend) → Python 3.11-slim (backend + repo)
- `railway.toml` — build/deploy config at repo root (`dockerfilePath = "dashboard/Dockerfile"`)

- `leadgen-agent/` — Google Maps scraper + lead qualifier
- `apptset-agent/` — home of the live AI SMS/email setter worker and its playbooks (below) + the newsletter; its older standalone SMS-setter scripts are legacy
- `onboarding-agent/` — client onboarding. **"Help me set up (my) service delivery for <client>"** (or "onboard <client>", "what's left to launch <client>") → run its `service-delivery-setup` skill (`onboarding-agent/.claude/skills/service-delivery-setup/SKILL.md`): scans the client's Marketing Setup checklist and walks Dylan through it step by step, ticking steps off as they're verified. DigiGrowth Booking is the default booking tool (below); Calendly/GoHighLevel only for clients already on them
- SMS setter (AI replies to Dylan's own cold SMS prospects): the model runs **locally on Dylan's PC via `claude -p` on his Claude subscription**, not the API — `apptset-agent/sms_setter_worker.py`, started at logon by the `DigiGrowth-SMSSetter` scheduled task (`apptset-agent/register-sms-setter-task.ps1`), so it only works while his computer is on. Server half (queue, drafts, Off/Draft/Auto mode, auto-send + Google Meet booking guardrails) is `dashboard/backend/sms_setter_ai.py` + `dashboard/backend/routers/sms_setter.py`. Brief lives in `apptset-agent/context/sms-setter-playbook.md`; replay real campaign threads with `apptset-agent/scripts/backtest_sms_setter.py` before changing it. It also **learns from Dylan's own replies**: when he texts a thread himself instead of its draft (handoff, skipped or edited draft), the worker distills a lesson into the `sms_setter_lessons` table and active lessons are appended to the system prompt (Inbox → LESSONS LEARNED to edit/turn off). Dylan can also schedule check-ins by hand (Inbox → + AI FOLLOW-UP, `ai_followup_by = 'dylan'`, note = his instructions)
- Email setter (AI replies to Dylan's own cold EMAIL prospects): same local worker and Claude subscription as the SMS setter, its own Off/Draft/Auto switch (Inbox → AI EMAIL). Server half `dashboard/backend/email_setter_ai.py` + `dashboard/backend/routers/email_setter.py`; replies go out on the prospect's own thread (same outreach mailbox) via `routers/email_inbox.py`'s send, bookings are tagged channel `email` so Analytics credits email. Brief = `apptset-agent/context/email-setter-rules.md` (email format/actions) + the SMS playbook (facts, price, booking stay single-sourced there)
- AI voice agent (client side, growth package): `dashboard/backend/client_voice_agent.py` + `routers/voice_agent.py`, Retell AI dialed over SIP from the client's own Twilio number (`client_voice_calls` table, every 20s). Calls new Meta leads ~3 min after the form (no text first) and funnel leads who ticked the booking page's call-consent box; no answer → redial → voicemail → text opener; retries +2h / next day / day after; stops on a text reply or booking. Meta leads only after the Instant Form's AI-call consent line is stamped live. Agents tab → Voice Agent; setup = Marketing Setup's "Set Up Voice Agent" guide. Needs `RETELL_API_KEY`. A **separate Database Reactivation voice agent** (own Retell LLM + agent, `react_*` config columns, `agent_kind = 'react'` call rows, own switch; Agents tab → Database Reactivation Voice Agent) places the last_call playbook's call: "you filled out our form on <date>, this is the final week of <offer>, wanted to let you know before it's gone". Same voice/name/consent rules as the ads agent, except a per-client `react_call_without_consent` switch (on for Advantage, Dylan 2026-11-17) lets it call leads without AI-call consent. Voice + script defaults (Kate, tone, pitch, screener handling) live in `client_voice_agent.py` and every client's agent is re-synced to them after each deploy
- Calendly watchdog (`dashboard/backend/calendly_watchdog.py`, every 30 min): Calendly can silently drop a webhook subscription (happened ~2026-11-05, bookings stopped reaching Appointments). It re-registers missing ones (Dylan's + clients'), imports upcoming bookings the webhook missed (`calendly_webhooks.resync_dylan_bookings`), and puts a To-Do on Dylan's list if it can't reconnect
- DigiGrowth Booking (our own Calendly replacement, default since 2026-11-06): `dashboard/backend/booking_engine.py` (slots, holds, Google Calendar via the dylanrg@ token, Stripe Connect direct charges, 100% to the clinic), `booking_conversion.py` (partial capture, unfinished-booking texts, funnel tracking, AI-agent hooks), `booking_autofill.py` (setup + page details from portal/website/funnel), `booking_page.py` (patient page), `routers/booking.py`; OS tab `BookingPanel.jsx` / `ClientBookingSetup.jsx`. Clinics share their Google Calendar with dylanrg@digigrowthllc.com and connect Stripe from their portal
- AI Client Success Manager (`dashboard/backend/client_success.py` + `routers/client_success.py`, daily 10:00 ET): **weekly campaign report** every Monday for each active client with a live campaign (auto-sent by email; text is a separate switch, off by default), and a **final report** when the campaign ends (campaign window = `campaign_launched_at` + `campaign_length_days`, default 30; goal + length = Marketing Setup step `campaign_goal`). The final report is **drafted for Dylan's approval** (To-Do + APPROVE & SEND in Reports) and carries "Your next campaign" (Claude's renewal plan from the results) and "Share your experience" (testimonial ask). Claude writes the analysis from the client's real `client_funnel` numbers. Reports are public pages at `/report/<slug>` with a questions/suggestions/rating form (replies → To-Do, answers show in the next report) and are listed in the client portal. Part 2, `csm_extras.py`: daily health score (red → at-risk To-Do), milestone texts every 30 min (first lead, halfway, goal hit; once each per campaign), onboarding check-ins drafted on day 1/3/7 until launch **that Dylan approves before they send**, and a lead-quality loop (the portal's appointment outcome card asks "good fit?" once Showed + Closed are picked → CRM tags + report + To-Do). Per client: Clients → client → Agents → Client Success Manager (`ClientSuccessAgent.jsx`). Shared wording: Business Resources → Outreach Templates → "Client Success Templates". Report page HTML: `client_report_html.py` (styled like the Patient Acquisition Blueprint: dark grid, clinic × DigiGrowth lockup, numbered sections; pages are stored at creation, so style changes only reach new reports). Numbers mirror the portal's Results tab; show-ups/new patients are flagged "Reported by your team". Every report has an "Appointments waiting on an outcome" section that loads live (`GET /report/<slug>/appointments`) and saves through the portal's outcome handler, so the clinic can fill in show/no-show, closed and notes from the report. The page's "New patients" and show-up / became-a-patient journey steps refresh live from `GET /report/<slug>/live` on load and after each save (the portal Results tab refetches on focus and every 60s). The funnel's "Reached" step = Instant Form leads who texted back or picked up an AI call. Artifact copies / final-report review: the `client-success-reports` skill (`.claude/skills/`)
- Client retention / churn (`dashboard/backend/client_retention.py`, 2026-11-21): one `client_renewals` row per finished campaign, opened when its final report is sent (or "Mark as sent"); Dylan records Renewed / Churned (reason) / Paused + plan + $/month on the client's Client Success Manager card ("Did they stay?"). Daily 10:10 ET: a newer campaign launch auto-marks renewed, a "let's talk about the next campaign" click shows as a hint, and a "Did <client> renew?" To-Do after 14 days pending. Analytics → CLIENT RETENTION (`RetentionView.jsx`, `GET /api/client-success/retention`): churn/renewal rate (out of renewed + churned), revenue kept/lost, reasons, and renewal rate split by goal hit, health band, report opened, wants-next, testimonial, outcomes marked, package, cost per booking

## Key Conventions

- **Auth**: HTTPBasic (`DASHBOARD_PASSWORD` env var) applied to all `/api` routes
- **SSE streaming**: always use `fetch()` + `ReadableStream` — never `EventSource` (can't POST with auth)
- **File persistence on Railway**: write to disk + call `github_push_file()` — Railway containers are ephemeral, `.git/` is absent, so git CLI fails; GitHub REST API is the only persistence path
- **Agent chat history**: stored in `agent_chats` table (JSONB `content` = full Anthropic content blocks to preserve tool_use/tool_result alternation)
- **Secrets**: all API keys and passwords (`ANTHROPIC_API_KEY`, `DASHBOARD_PASSWORD`, `DASHBOARD_URL`, `PLACES_API_KEY`, etc.) live in the shared `digigrowth` Doppler vault (project `digigrowth`, config `prd` for production), not in any local `.env` file. Fetch via `doppler secrets get <NAME> --project digigrowth --config prd --plain`. Railway pulls the same vault at deploy time.
- **NEVER touch**: `.env`, `credentials.json`, `settings.local.json`
- **Screenshots/visual QA artifacts**: never save `.png`/`.jpg`/`.jpeg` files to the repo root (or any tracked project directory) for browser screenshots, visual checks, or other scratch images — use the session's scratchpad/temp directory instead. Root-level images are `.gitignore`'d as a backstop, but avoid creating them there in the first place.

## Frontend Patterns

- Theme: dark navy glassmorphism (`#090f26` base, `#3a7bd5` accent blue)
- Fonts: `Inter` (body/UI text, since the 2026-11-17 refresh), `Space Grotesk` (headings, big numbers), `Share Tech Mono` (legacy metadata, avoid in new UI)
- CSS classes: `glass-card`, `glass-card-sm`, `stat-card`, `dg-input`, `btn btn-primary`, `btn btn-secondary`, `sec-label`, `dg-divider`
- **Design kit `src/ui.jsx`** (2026-11-17): `T` color/font tokens (mirrors the `--dg-*` CSS vars in index.css) plus `Card`, `PageHeader`, `SectionTitle`, `Tabs`, `Pill`, `Toggle`, `Stat`, `Progress`, `Empty`, `Loading`, `HealthBadge`, `inputStyle`. Build new or redesigned screens from these (sentence-case buttons, no all-caps mono labels). The Clients panel and `ClientSuccessAgent.jsx` are the reference examples
- Sidebar nav is grouped (`NAV_GROUPS` in App.jsx: Sales / Clients / Business). Add a panel to a group, not a flat list
- All styles are inline React style objects — no CSS modules, no Tailwind
- Nav panels: exported default function in `src/panels/*.jsx`, registered in `App.jsx`

## Backend Patterns

- All routers imported in `main.py` and mounted at `/api` with `Depends(require_auth)`
- DB queries use `asyncpg` pool (`get_pool()` from `db.py`)
- File paths resolved with `pathlib.Path(__file__).parent...` — never hardcoded
- `BLOCKED_FILENAMES = {".env", "credentials.json", "settings.local.json"}` checked on every file op
- Path sandbox: `(root / rel).resolve()` then `.relative_to(root)` — raises 403 on traversal
